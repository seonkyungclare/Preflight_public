# Preflight 개선 제안

> 2026-07-29 · 류진한
> PRD → 디자인 → Figma로 이어지는 작업 흐름에 Preflight를 넣어보다가 발견한 것들과, 같이 상의하고 싶은 방향입니다.

---

## 한눈에 보기

Preflight를 실제 흐름에 넣어보려고 안을 들여다봤습니다. **구조와 방향은 좋은데, 점수가 나오는 과정에 신뢰를 깎는 문제 몇 개가 있었습니다.** 고치는 방법은 대부분 명확합니다.

그리고 **크게 상의하고 싶은 게 두 가지** 있습니다.

| | 제안 |
|---|---|
| **하나** | 점수를 앞에 내세우지 말고 **"남은 결정 몇 건"**을 앞에 보여주는 건 어떨까요 |
| **둘** | 도구의 성격을 **"PM이 공유 전에 혼자 점검하는 도구"**로 잡는 건 어떨까요 |

아래에 이유를 적었습니다.

---

## 먼저 — 잘 되어 있다고 본 것

이건 그대로 두거나 오히려 더 살리면 좋겠다고 본 부분입니다.

**1. "A안이냐 B안이냐"로 묻는 질문 방식**
가장 좋은 부분이라고 생각합니다. PM에게 "이거 부족해요"라고 하면 뭘 어떻게 채우라는 건지 막막한데, **선택지 두 개로 물으면 답이 바로 나옵니다.** 실제로 제가 만든 다음 단계 도구(PRD를 UX 문서로 바꾸는 것)가 이 질문들을 그대로 받아서 쓰고 있어요.

**2. 디자이너용 / 개발자용 체크리스트를 나눠놓은 것**
"PM한테만 좋은 문서"가 되는 걸 막는 장치가 이미 구조로 들어가 있습니다. 각자 쓰는 말도 다르게 해놨고요.

**3. 왜 이 점수인지 보여주는 것**
항목별 점수와 그 이유가 나오니까 "그냥 60점"보다 훨씬 낫습니다. 개선할 지점을 찾을 수 있어요.

---

## 발견한 문제들

쉬운 말로 정리했습니다. 심각한 순서입니다.

### 1. 점수 계산을 AI가 직접 하고 있습니다 ⭐

항목별 점수를 매기고 **총점 계산까지 AI가 합니다.** 프로그램은 그 숫자를 그대로 받아서 화면에 띄웁니다.
→ 항목 점수를 다 더해도 총점이 안 맞는 경우가 생겨도 **아무도 모릅니다.**
→ **고치는 법**: 총점은 프로그램이 직접 계산하게. 항목 점수만 AI에게 받으면 됩니다. 코드로 몇 줄이면 되는데 효과가 제일 큽니다.

### 2. 채점할 때마다 다른 문서가 딸려 들어가고 있습니다 ⭐

Preflight가 AI를 부를 때, **폴더에 있던 설정 문서들이 자동으로 같이 읽힙니다.** 지금 확인된 것만 3개인데, 그중 하나는 **예전 버전 채점표**입니다.
→ 즉 지금은 채점할 때마다 **서로 다른 두 개의 채점표**를 AI가 동시에 받고 있습니다.
→ 게다가 그중 하나는 개인 컴퓨터에 있는 설정이라, **PM들에게 나눠주면 사람마다 점수가 다르게 나옵니다.**
→ **고치는 법**: AI를 부를 때 그 문서들이 안 딸려오게 격리 + 쓰는 AI 모델도 고정.

### 3. 채점 기준이 6군데에 흩어져 있고 이미 서로 안 맞습니다

같은 기준이 여러 파일에 나뉘어 적혀 있습니다. 그래서 이미 어긋난 게 있어요:
- 판정 문구가 **3종류인데 다 다릅니다** ("개발 준비 완료" / "Ready" / "즉시 킥오프")
- 결과 화면에 **판정 배지가 두 개 겹쳐서** 뜨는 것도 이것 때문입니다
- 배점 설명도 문서에는 "25점 만점", 실제 채점에는 "10점 × 2.5"로 갈려 있습니다

→ **고치는 법**: 기준을 한 곳에 모으고 나머지는 거기를 가져다 쓰게. 그러면 앞으로 배점을 바꿀 때 **한 곳만 고치면 됩니다.**

### 4. AI 응답이 조금만 어긋나면 결과가 통째로 날아갑니다

응답 형식이 살짝 안 맞으면 30초~1분 기다린 분석이 **다시 시도도 없이 사라집니다.** 항목 하나가 비어 있으면 화면이 아예 안 뜨기도 합니다.
→ **고치는 법**: 한 번 다시 시도 + 실패해도 원본 내용은 보여주기.

### 5. "개발 준비 완료"라는 문구가 실제보다 넓게 약속하고 있습니다

80점을 넘으면 "개발 준비 완료, 즉시 킥오프 가능"이라고 뜹니다. 그런데 **실제로 보는 건 화면 설계에 필요한 것들**입니다. 데이터 규칙이나 연동 같은 건 안 봅니다.
→ 이대로 두면 도장 받은 PRD를 받은 개발자가 "이거 착수 못 하는데요"라고 하게 됩니다. 도구 신뢰가 여기서 깎입니다.
→ **고치는 법**: 문구를 **"디자인 착수 가능"**으로 정확하게. 대신 개발 쪽에 필요한 것들은 점수와 별개로 **"개발 착수 전 확인할 것" 목록**으로 보여주기.

### 6. PM 템플릿과 채점 기준이 서로 싸우고 있습니다 ⭐

무신사 PRD 템플릿에는 **"PM은 화면을 그리지 않는다"**고 명시되어 있습니다. 그런데 Preflight 배점은 **화면 목록 25% + 화면별 상태 25% = 절반**이 화면 관련입니다.
→ 그래서 **템플릿대로 성실히 써도 40점대**가 나옵니다. PM 잘못이 아니라 채점 기준이 요구하는 게 애초에 템플릿에 없는 것들이에요.
→ 이대로면 PM들이 도구를 안 쓰거나, 점수를 위해 억지로 화면을 그리게 됩니다.
→ **고치는 법**: 화면 관련 배점은 PRD 채점에서 빼고, **다음 단계(UX 문서) 채점으로 옮기기.** 없애는 게 아니라 **묻는 대상을 바꾸는 것**입니다. PRD에는 화면 대신 "화면을 정할 수 있는 재료"(범위·정책·대상)가 있는지를 묻고요.
→ 화면 목록을 써 온 PM에게는 **감점 대신 가산점**을 주면 됩니다.

### 7. 모른다고 솔직하게 쓰면 손해입니다

"이 부분은 아직 미정"이라고 정직하게 적은 것과, **아예 언급도 안 한 것을 똑같이 감점**합니다.
→ 점수 올리는 가장 빠른 길이 **없는 정책을 지어내서 쓰는 것**이 됩니다. 그걸 개발자가 믿고 만들면 사고로 이어지고요.
→ **고치는 법**: "미정"이라고 밝힌 건 덜 깎고, 대신 확인 질문으로 넘기기.

### 8. 결과가 안 남습니다

점수를 저장하거나 내보낼 방법이 없습니다.
→ 41점 → 68점 → 82점으로 좋아졌다는 걸 **증명할 수가 없습니다.** 다음 단계 도구에 넘길 때도 손으로 복사해야 하고요.
→ **고치는 법**: 결과 내려받기 + 다시 돌렸을 때 뭐가 달라졌는지 비교.

## 상의하고 싶은 것 ①: 점수 대신 "남은 결정"을 앞에 두면 어떨까요

### 왜 이런 생각을 했나

점수는 직관적이지만, 이런 걱정이 있습니다.

- **PRD에는 정답이 없습니다.** 그런데 점수가 나오면 평가받는 느낌이 들고, 그게 도입과 활용을 떨어뜨릴 수 있어요.
- **78점과 82점의 차이가 실제로는 의미가 없습니다.** 같은 문서를 두 번 넣어도 몇 점씩 흔들리거든요. 그런데 그 사이에 판정이 갈립니다.
- **"점수를 올린다"는 목표는 방향이 좀 이상해집니다.** 문서를 좋게 만드는 게 아니라 점수 잘 나오는 문구를 쓰게 될 수 있어요.

### 제안하는 모습

**화면 앞에는 이렇게:**

> **디자인 착수까지 남은 결정 3건**
> 화면 상태 ⚠️ 보완 · 정책 ✅ 충분 · 예외 처리 ❌ 누락 · 범위 ✅ 충분

**점수는 접어서 아래에** (궁금하면 펼쳐보는 정도로)

이렇게 하면:
- "몇 점이냐"가 아니라 **"뭘 더 정하면 되냐"**로 대화가 바뀝니다
- 3건 → 1건 → 0건은 몇 점 올랐는지보다 **손에 잡힙니다**
- 점수가 흔들려도 **"충분/보완/누락" 3단계는 잘 안 뒤집힙니다**
- 억지로 점수 올리는 게 아니라 **질문을 없애는 게 목표**가 되니, 잘하려고 노력한 게 곧 문서 개선이 됩니다

### 점수를 아예 없애자는 건 아닙니다

점수 계산은 **안에서 계속 돌리되 화면에서만 내리자**는 쪽입니다. 이유는 하나예요 — 나중에 **배점을 바꿨을 때 좋아졌는지 재려면 숫자가 필요**하거든요. 그래서 "없애기"가 아니라 "뒤로 빼기"입니다.

## 상의하고 싶은 것 ②: 도구의 성격을 이렇게 잡으면 어떨까요

**"PM이 다른 직군에 공유하기 전에, 그리고 상위 보고 전에 — 혼자 미리 점검해보는 도구"**

이렇게 잡으면 좋은 이유:

| | |
|---|---|
| **평가가 아니라 리허설** | "누가 나를 채점한다"가 아니라 "공유 전에 내가 먼저 본다"가 됩니다. 도입 저항이 확 줄어요 |
| **사람 리뷰를 대체하지 않는다는 게 명확** | PM 내부 리뷰도, PD·개발 리뷰도 그대로 합니다. Preflight는 그 앞에서 **미리 걸러주는 것**뿐입니다 |
| **PM에게 실제로 도움이 됨** | 공유하고 나서 "이거 빠졌는데요" 소리를 듣는 것보다, 미리 알고 채워서 내는 게 낫잖아요 |

이 성격 규정이 나중에 PM들에게 설명할 때도 핵심 메시지가 될 것 같습니다.

## 고치는 순서 제안

한 번에 다 바꾸지 말고 나눠서 가면 좋겠습니다. **앞의 두 덩어리가 "점수를 믿을 수 있게" 만드는 부분**이고, 채점 기준 자체를 바꾸는 건 그 다음입니다.

| 순서 | 무엇 | 왜 이 순서인가 |
|---|---|---|
| **1** | 딸려 들어오는 문서 차단 + AI 모델 고정 + 시간 초과 처리 | **제일 먼저.** 이걸 안 하면 이후에 "좋아졌는지"를 잴 수가 없습니다 |
| **2** | 지금 상태로 샘플 몇 개 돌려서 **기준선 기록** | 나중에 비교할 "before"가 필요합니다 |
| **3** | 채점 기준을 한 곳으로 모으기 (기준 내용은 그대로) | 여기까지는 **결과가 달라지면 안 됩니다.** 정리만 하는 단계 |
| **4** | 총점을 프로그램이 계산 + 결과 안 날아가게 | 여기까지가 "숫자를 믿을 수 있게" |
| **5** | 채점 기준 자체를 바꾸기 + 표시를 "남은 결정"으로 전환 | **상의한 방향이 여기서 반영됩니다.** 한 번에 바꿔야 설명하기도 좋습니다 |
| **6** | 배점 미세 조정 | 실제 PRD 돌려보고 숫자만 다듬기 |
| **7** | 결과 내려받기·비교 | |

3번까지 해두면 5번에서 배점을 바꿀 때 **한 곳만 고치면 되고**, 잘못되면 그 부분만 되돌릴 수 있습니다.

## 따로 봐야 할 것: 목업

지금 하이파이 목업이 **PRD에 없는 요소들(팝업·로딩 표시 등)을 확정된 것처럼 그립니다.** 그리고 **40점짜리 PRD로도 그럴듯한 목업이 나옵니다.**
→ PD가 그걸 보고 "정해진 거구나" 하고 받아들일 위험이 있어요.
→ PRD에 근거가 없는 부분은 **"PRD에 없음 — 추정"**이라고 표시하는 정도면 될 것 같습니다. 이건 다른 작업들과 상관없이 따로 할 수 있고, **PM들에게 나눠주기 전에는 해두는 게 좋겠습니다.**

---

## 안 건드리려는 것

작업이 커지지 않게 선을 그어뒀습니다.

- 화면 구조 전면 개편 — 이번 문제의 원인이 아닙니다
- 분석 중 진행률을 실제 진행률로 바꾸는 것 — 지금은 타이머로 도는 가짜인데, 고치려면 구조를 바꿔야 해서 이번 목표와 상관없습니다
- 그 외 "있으면 좋은" 기능들 — 신뢰도 확보가 먼저입니다

---

## 정리

- Preflight의 **방향과 구조는 좋습니다.** 특히 A/B 선택지 질문은 그대로 살리면 좋겠어요
- 다만 **점수가 나오는 과정에 신뢰를 깎는 문제**가 몇 개 있고, 대부분 고치는 방법이 명확합니다
- 크게 상의하고 싶은 건 두 가지입니다 — **점수를 뒤로 빼고 "남은 결정"을 앞에** / **셀프 점검 도구로 성격 잡기**
- 특히 **템플릿과 채점 기준이 싸우는 문제(6번)**는 PM들에게 확산하기 전에 꼭 풀어야 할 것 같습니다

편하실 때 이야기 나눠요. 제가 잘못 본 부분이나 원래 의도가 있었던 부분이 있으면 알려주세요.
