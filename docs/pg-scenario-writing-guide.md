## 왜 이 두 섹션이 점수의 40%인가

Preflight v3는 템플릿 11개 섹션에 감점 예산을 나눠 두고, 없는 항목만큼 깎습니다.
그중 **Actor & 권한 체계 20점, 유저 시나리오 20점**으로 두 섹션이 절반에 가깝습니다.
게다가 두 섹션은 **하드 게이트**를 갖고 있어, 다른 섹션을 아무리 잘 써도 아래 상한을 넘지 못합니다.

| 상황 | 점수 상한 |
| :--- | :--: |
| 유저 시나리오 섹션이 없다 | 59 (Rewrite) |
| Actor 정의 표가 없다 | 59 (Rewrite) |
| 본문에 나오는 Actor 중 표에 없는 유형이 있다 | 79 (Refine) |
| 화면 요구사항 섹션이 없다 | 69 |

## 3. Actor & 권한 체계 — 20점

### 3.1 Actor 정의 표 (12점)

**감점 규칙**
- 본문 어디든 등장하는 Actor가 표에 없으면 1개당 −3 (상한 8)
- 표에 있는 Actor라도 `정의` · `진입 경로` · `권한 범위` 중 빈 칸이 있으면 1칸당 −1 (상한 4)

**"다른 Actor"의 기준은 권한입니다.** 같은 회사 사람이어도 할 수 있는 일이 다르면 따로 씁니다.

| ❌ 이렇게 쓰면 | ✅ 이렇게 나눕니다 |
| :--- | :--- |
| 내부 담당자 | 담당 MD (브랜드 적합성 심사) / 운영 심사자 (표준 심사·승인·반려) / HO (등록·검수) |
| 파트너 | 파트너 PO (신청·동의) / 대행사 (파트너를 대리해 작성만, 제출 불가) |
| (표에 없음) | 시스템 (배치 반영·자동 상태 전이·Bypass 대조·계약 자동 발송) |

**"시스템"도 Actor입니다.** 상태 전이표의 "주체" 열에 시스템이 있으면 Actor 표에도 있어야 합니다.

**Preflight가 Actor를 찾는 곳** — 이 중 하나에라도 등장하면 표에 있어야 합니다.
- 유저 시나리오의 주어 ("파트너는…", "내부 담당자는…")
- Workflow의 단계 주체
- 화면 요구사항의 "관련 Actor" 열
- 정책표·상태 전이표의 "주체" 열
- 알림 수신자 ("운영팀에 알림", "영업팀 개별 안내")

**표 예시**

| # | Actor | 정의 | 진입 경로 | 권한 범위 |
| :-- | :--- | :--- | :--- | :--- |
| 1 | 파트너 PO | 입점을 신청하는 브랜드 담당자 | 파트너센터 > 입점 신청 | 본인 신청 건 작성·제출·회수·재제출, 계약 동의 |
| 2 | 담당 MD | 브랜드 적합성을 선행 심사하는 사업 담당자 | 운영 어드민 > 심사 > 적합성 | 배정 건 조회, 적합/부적합 판정 |
| 3 | 운영 심사자 | 표준 심사·승인·반려를 수행하는 운영 담당자 | 운영 어드민 > 심사 > 검토 대기 | 배정 건 조회, 승인·반려·보류 |
| 4 | 시스템 | 배치·자동 전이 처리 주체 | — | Bypass 대조, 계약 자동 발송, EXPIRED 전이, 외부 반영 배치 |

### 3.2 권한 매트릭스 (4점) · 3.3 데이터 접근 범위 (2점) · 3.4 권한 없는 진입 (2점)

- 3.2는 **기능 × Actor** 표에 C / R / U / D / 승인 중 해당하는 것을 씁니다. 표가 없으면 −4, 기능이 일부 빠지면 −2.
- 3.3은 Actor(또는 Actor의 상태)별로 **어디까지 볼 수 있고 고칠 수 있는지**. "본인 건만", "배정 건만", "전체".
- 3.4는 **권한 없이 진입하면 어떻게 되는지** 한 줄. "차단 화면 + 목록으로 돌아가기", "403 후 로그인 페이지 리다이렉트".

## 5. 유저 시나리오 — 20점

### 5.1 전체 시나리오 맵 (6점)

To-Be 완성형을 먼저 씁니다. 마일스톤은 생각하지 않습니다.

**형식**: `S-nnn` ID · Actor · 한 줄 시나리오 · 관련 Feature · 우선순위

**"누가 무엇을 할 수 있다"로 씁니다. 기능 나열이 아닙니다.**

| ❌ 기능 나열 (partial) | ✅ 사용자 도달 상태 (present) |
| :--- | :--- |
| 신청서 제출 기능 | 파트너 PO는 신청서를 작성하고 제출할 수 있다 |
| 상태 조회 | 파트너 PO는 제출한 신청의 진행 상태를 확인할 수 있다 |
| 일괄 승인 | 운영 심사자는 검토 대기 건을 여러 개 골라 한 번에 승인할 수 있다 |

**모든 Actor는 시나리오를 1개 이상 가져야 합니다.** 3.1에 정의했는데 시나리오가 없는 Actor는 1개당 −1이고, 교차 검증 카드에 "시나리오 없는 Actor"로 표시됩니다. 시스템 Actor도 "시스템은 승인된 건을 외부 시스템에 자동 반영한다"처럼 씁니다.

### 5.2 Milestone 정의 (4점)

시나리오 × 마일스톤 표. 셀에는 `✅ 전체 지원` / `◐ 부분 지원` / `— 미포함` 셋 중 하나. 마일스톤 열 제목에 목표 시점을 넣습니다 (M1 (26.11)).
`◐`인 칸은 오른쪽 "이번 달성선" 열에 **어디까지인지 문장으로** 씁니다. "목록에서 현재 상태만. 이력·타임라인은 M2".

### 5.3 이번 Milestone 도달선 (4점)

두 가지가 있어야 present입니다.
1. PRD가 끝났을 때 사용자가 무엇을 할 수 있는지 **3~5문장**
2. **미지원 항목 표**: 미지원 항목 · 안 하는 이유 · 대체 수단 · 안내 주체 · 해소 시점

미지원 항목 표가 없으면 "이번에 안 하는 것"이 디자인·개발 단계에서 다시 질문으로 돌아옵니다.

### 5.4 시나리오 상세 (6점)

`✅`와 `◐` 시나리오마다 씁니다. `—` 는 쓰지 않습니다.

```
S-003. 운영 심사자는 배정된 신청을 검토하고 승인·반려한다  [F3]

[진입]
1. 운영 어드민 > 심사 > 검토 대기 목록으로 진입한다.        → SC-11

[본 흐름]
2. 신청 건을 선택해 상세를 확인한다.                        → SC-12
3. 승인 처리 → 상태 전이, 파트너 알림                       → §7 T-02
4. 반려 시 사유 입력 (미입력 시 처리 차단)                   → §7 T-03

[예외]
- 다른 심사자가 이미 처리한 건 → 처리 차단, 현재 상태 안내
- 배정되지 않은 건에 직접 URL 접근 → 접근 차단              → SC-12 권한없음
- 일괄 승인 시도 → M1 미지원. 버튼 미노출
```

**세 가지가 Preflight 채점에 직접 걸립니다.**

| 항목 | 없으면 |
| :--- | :--- |
| `[진입]` `[본 흐름]` `[예외]` 세 블록 | 해당 시나리오는 partial |
| 본 흐름 단계의 `→ SC-nn` 화면 참조 | "화면 참조 없는 시나리오"로 표시, §8.2 교차 일치 감점 |
| 예외 1개 이상 | partial. 예외가 없는 시나리오는 사실상 없습니다 |

`→ SC-nn`으로 가리킨 화면은 **8. 화면 요구사항에 같은 ID로 실재**해야 합니다. 없으면 교차 검증 카드에 Major로 올라옵니다.

## 작성 체크리스트

제출 전에 아래를 훑어보세요. 하나라도 ❌면 그 자리에서 감점됩니다.

**Actor**
- [ ] 본문(시나리오·Workflow·화면·정책표·알림)에 나오는 모든 Actor 유형이 3.1 표에 있다
- [ ] 권한이 다른 사람은 다른 Actor로 나눴다 (담당 MD ≠ 운영 심사자)
- [ ] 상태를 바꾸는 "시스템"이 있으면 Actor 표에 있다
- [ ] 모든 Actor 행에 정의·진입 경로·권한 범위가 채워져 있다
- [ ] 기능 × Actor 권한 매트릭스가 있다
- [ ] 권한 없이 진입했을 때 동작이 한 줄 있다

**유저 시나리오**
- [ ] S-nnn ID가 있고 Actor 열이 3.1의 이름과 철자까지 같다
- [ ] 모든 Actor가 시나리오를 1개 이상 가진다
- [ ] "누가 무엇을 할 수 있다" 문장이다 (기능명 나열이 아니다)
- [ ] Milestone 표에 ✅/◐/— 와 시점이 있고, ◐ 는 어디까지인지 문장이 있다
- [ ] 도달선 3~5문장 + 미지원 항목 표가 있다
- [ ] ✅·◐ 시나리오마다 [진입]/[본 흐름]/[예외]가 있다
- [ ] 본 흐름 단계가 → SC-nn 을 가리키고, 그 SC-nn 이 8. 화면 요구사항에 있다

## 결과 화면에서 확인하는 법

분석 결과 **요약 탭** 상단에 다음이 순서대로 나옵니다.
1. 게이트 배너 — 상한에 걸렸다면 왜 걸렸는지
2. 섹션 커버리지 — §3, §5 행을 펼치면 어느 하위 항목에서 몇 점이 빠졌는지
3. Actor 정의 현황 — 정의된 Actor의 3필드 충족도, 그리고 **본문에만 등장하는 Actor**
4. 유저 시나리오 현황 — 맵/마일스톤/상세 개수, 시나리오 없는 Actor, 화면 참조 없는 시나리오
5. 교차 검증 — 섹션 간 연결이 끊긴 곳

미정의 Actor는 자동으로 **PO 질문 탭**에 [비즈니스] 질문으로도 올라옵니다.
